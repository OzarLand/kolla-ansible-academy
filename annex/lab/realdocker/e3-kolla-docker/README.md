# e3: the real `kolla_docker` module (kolla-ansible ussuri-eol) against a real Docker daemon

## Purpose

The study's statements about `kolla_docker` (stop timeout, restart vs recreate, `compare_container` and the exit codes
of `kolla_set_configs --check`, one-shot containers, the swift `start_container` pattern, the bifrost reconfigure)
were [CODE] or came from feeding the module code arguments without a daemon. This experiment runs the unmodified
`ansible/library/kolla_docker.py` of kolla-ansible `ussuri-eol` through Ansible 2.9.27, with arguments shaped exactly
like the role tasks (the task bodies are copied from the roles, `common_options: "{{ docker_common_options }}"` from
the real `group_vars/all.yml`), against a real Docker daemon and containers built on the kolla Ussuri start path
(`reallab/base:ussuri`).

| Images | `e3-rabbitmq:ussuri`, `e3-heat-api:ussuri`, `e3-swift-rsyncd:ussuri`, all `FROM reallab/base:ussuri` (ubuntu:18.04, dumb-init 1.2.1-1, sudo 1.8.21p2-3ubuntu1.6, python3 3.6.7); `rsync` 3.1.2-2.1ubuntu1.6 from bionic main (not an OpenStack package, so the Ussuri image very likely had the same) |

No Cloud Archive package is involved: no RabbitMQ, MariaDB, OVS, libvirt or QEMU binary is installed (see stand-ins).

## Method

`run.sh` (idempotent; needs `reallab/base:ussuri`) creates the e3 venv (`setup-venv.sh`), builds the three images
(`build.sh`), then runs 23 steps. Each step is one `ansible-playbook` run of a playbook in [playbooks/](playbooks/)
against `localhost` (local connection, `become: true`, `ANSIBLE_LIBRARY` = the kolla-ansible `ansible/library`).

- **Variables.** Every play loads, in this order, the real `group_vars/all.yml`, the real
  `roles/{rabbitmq,heat,swift}/defaults/main.yml`, then [playbooks/vars-e3.yml](playbooks/vars-e3.yml). So
  `docker_common_options` is the real dict: `graceful_timeout: 60`, `client_timeout: 120`,
  `restart_policy: unless-stopped`, `environment: {KOLLA_CONFIG_STRATEGY: COPY_ALWAYS}` (printed in
  [out/a0-common-options.json](out/a0-common-options.json)), and `rabbitmq_services` / `heat_services` are the real
  dicts. `vars-e3.yml` changes only names (isolation prefix), host paths, images and fake secrets, plus
  `role_rabbitmq_groups` and `project_name`, which `site.yml:541-553` passes as role parameters.
- **Tasks.** Copied verbatim from `roles/rabbitmq/tasks/{check-containers,bootstrap}.yml`, the handler task of
  `roles/rabbitmq/tasks/restart_services.yml`, `roles/service-stop/tasks/main.yml`,
  `roles/heat/tasks/bootstrap_service.yml`, `roles/swift/tasks/start.yml` (swift-rsyncd) and
  `roles/bifrost/tasks/reconfigure.yml` (generated by [gen_bifrost.py](gen_bifrost.py)). Each playbook header says what
  was changed. The config files are rendered by [render.py](render.py) from the real templates (`rabbitmq.json.j2`,
  `heat-api.json.j2`, `swift-rsyncd.json.j2`, `rsyncd.conf.j2`), with Kolla-Ansible's modes (dirs 0770, files 0660).
- **Recording.** A callback plugin ([plugins/e3_record.py](plugins/e3_record.py)) keeps every `kolla_docker` and
  `command` result unabridged; [trim.py](trim.py) reduces it to [out/results/](out/results/). Its
  `module_args(effective)` is `invocation.module_args`, which `kolla_docker` overwrites with its *merged* parameters
  (`common_options` plus task arguments, `kolla_docker.py:1037-1056`), so it shows the values the module used. The
  Ansible display (default callback, `profile_tasks`) is in [out/ansible/](out/ansible/). A background
  `docker events` stream gives daemon-side timestamps of every signal, exec and lifecycle event:
  [out/events.txt](out/events.txt) per step, [out/timings.txt](out/timings.txt) for stop durations. Container id and
  start time after each step are in [out/state.txt](out/state.txt); `kolla_set_configs --check` run by hand exactly as
  the module runs it (`docker exec -u root <c> /usr/local/bin/kolla_set_configs --check`) is in
  [out/check-rc.txt](out/check-rc.txt).
- **Stand-ins** (said again where they matter):
  - `/usr/sbin/rabbitmq-server` in `e3-rabbitmq` is a Python stand-in, **not RabbitMQ**. It logs its start (first line
    of `/etc/rabbitmq/rabbitmq.conf`, `RABBITMQ_CLUSTER_COOKIE`, the cookie file) and every signal it receives, and it
    **ignores SIGTERM**, like a service still busy when `docker stop` arrives. Log:
    [out/a-c-standin.log](out/a-c-standin.log).
    The real kolla rabbitmq `extend_start.sh` runs in front of it.
  - `heat-manage` and `openstack` in `e3-heat-api` are stand-ins: `db_sync` and `domain create` succeed, `user create`
    fails with an HTTP 500 message on stderr. The real heat-base and heat-api `extend_start.sh` run.
  - `e3-swift-rsyncd` runs the **real** rsync daemon with the real kolla `extend_start.sh` and sudoers.
  - The files listed in the rabbitmq and heat `config.json` other than `config.json` are one-line placeholders with
    a version marker.
- **Isolation.** Containers `e3_rabbitmq`, `e3_rabbitmq_bootstrap`, `e3_rmqv_bootstrap`, `e3_bootstrap_heat`,
  `e3_swift_rsyncd`; volumes `e3_rabbitmq`, `e3_rmqv`, `e3_kolla_logs` (instead of `kolla_logs`); rsync on
  127.0.0.1:18373 (instead of 10873). All removed at the end; images kept.

## Lab fidelity: two incompatibilities found before the tests

**L1. docker SDK 4.4.4 does not work with requests 2.32.** With the study's shared venv (requests 2.32.4, urllib3
2.2.3) the module fails before reaching the daemon: `docker.errors.DockerException: Error while fetching server API
version: Not supported URL scheme http+docker`. This is a client-library incompatibility, not API negotiation. e3
uses its own venv with the same Ansible 2.9.27 and docker SDK 4.4.4 but requests 2.23.0 and urllib3 1.25.8 (early
2020 releases); API negotiation then works (`auto` → 1.56), so `api_version` is not set anywhere.

**L2. On Docker 29 the unmodified module cannot compare an existing container** (step `a1x`, run without the shim):

```
File ".../kolla_docker.py", line 793, in recreate_or_restart_container
File ".../kolla_docker.py", line 348, in check_container_differs
File ".../kolla_docker.py", line 516, in compare_dimensions
KeyError: 'KernelMemory'
```

([out/ansible/a1x-handler-without-shim.txt](out/ansible/a1x-handler-without-shim.txt); no daemon event in that step,
[out/events.txt](out/events.txt)). Docker 29 omits `HostConfig.KernelMemory` at every API version tried (1.40 to 1.43
and 1.56); Docker 19.03/20.10 returned `"KernelMemory": 0` (API documentation; not observed here). `compare_dimensions`
reads it unconditionally (`kolla_docker.py:516`), so `compare_container`, `recreate_or_restart_container` and
`start_container` fail on any existing container. Pinning `api_version` cannot help. All other fields the module
compares have the old shape on Docker 29 (checked: image id, binds, volumes, labels, `PidMode`, `IpcMode`, `Privileged`,
dimensions, `Ulimits`, `State.Status`, the `Up ...` status string). The module file is used **unmodified**; instead
[compat/e3_docker_compat.py](compat/e3_docker_compat.py), loaded into the e3 venv through a `.pth` file, adds
`KernelMemory: 0` to inspect responses when it is absent, restoring the old response shape and nothing else.
`E3_NO_SHIM=1` disables it (step `a1x`). Every other step uses the shim.

## Results

### (a) Stop duration of a restart: 10 s, not 60 s

The stand-in ignores SIGTERM. Daemon events ([out/events.txt](out/events.txt)) and [out/timings.txt](out/timings.txt):

| Step | Action (as the roles call it) | `graceful_timeout` effective | SIGTERM → SIGKILL | Container |
|---|---|---|---|---|
| a2 | handler `recreate_or_restart_container`, parameters unchanged | 10 | 10.01 s | same id, restarted |
| a3 | `restart_container` with `common_options` | 10 | 10.01 s | same id |
| a4 | control: same, plus task-level `graceful_timeout: 20` | 20 | 20.01 s | same id |
| a5 | `stop_container` (`service-stop` shape) | 10 | 10.01 s | exited |
| c1 | handler after a config change (restart) | 10 | 10.01 s | same id |
| c2 | handler after an env change (recreate) | 10 | 10.01 s | new id |

```
== a2-handler-unchanged  (playbook wall time 12.03 s)
  +  1.793 s  e3_rabbitmq            kill  signal=15
  + 11.805 s  e3_rabbitmq            kill  signal=9
  + 11.838 s  e3_rabbitmq            stop
  + 11.840 s  e3_rabbitmq            die  exitCode=137
  + 11.936 s  e3_rabbitmq            start
```

(`out/events.txt` lines 12-17; `timings.txt`: `stop of e3_rabbitmq SIGTERM->SIGKILL 10.01 s`.) The module
results show the merge: `docker_common_options` carries `"graceful_timeout": 60`
([out/a0-common-options.json](out/a0-common-options.json)), the effective arguments carry `"graceful_timeout": 10`
([out/results/a2-handler-unchanged.json](out/results/a2-handler-unchanged.json), `a3`, `a5`, `c1`, `c2`). The stand-in
log shows one `got SIGTERM -> ignored, still running` per stop and nothing else (SIGKILL cannot be caught), and
`ppid=1` at each start: the service is dumb-init's direct child and received the forwarded SIGTERM
([out/a-c-standin.log](out/a-c-standin.log)). The a4 control (20.01 s) shows that the daemon honours whatever timeout
the module sends, so the 10 s is the module's default (`kolla_docker.py:991`) beating `common_options`
(`:1037-1047`). `client_timeout` behaves the same way: with `-e docker_client_timeout=300`, `docker_common_options`
carries `"client_timeout": "300"` ([out/a7-common-options-ct300.json](out/a7-common-options-ct300.json)) and the
module uses `"client_timeout": 120` ([out/results/a7-client-timeout-300.json](out/results/a7-client-timeout-300.json)).

Also observed: `recreate_or_restart_container` with unchanged parameters and `COPY_ALWAYS` restarts (same id, new
`StartedAt`, [out/state.txt](out/state.txt) a1 → a2). After a5 (`stop_container`), the next deploy (a6) **recreates**
the stopped container (`destroy`, `create`, `start`, new id 006fb1812d5a; no `--check` exec): `compare_container_state`
(`running` wanted, `exited` found) makes `check_container_differs` true before `compare_config` is reached.

### (c) `recreate_or_restart_container`: config change vs environment change

Both steps run the deploy flow (check-containers, bootstrap.yml, flush handlers, the real handler task):

- module result `changed: false`

## Caveats

- **Docker 29.9.2, not 19.03/20.10.** The stop sequence (SIGTERM, wait `t`, SIGKILL) is long-standing daemon
  behaviour, and the a4 control shows the timeout comes from the request, but every duration here is a lab
  measurement on this daemon (cgroup v1, this sandbox), not a production number. The unknown-container `docker exec`
  rc (1) is the Docker 29 CLI's.
- **The module needed a response-shape shim** (L2). It only adds `KernelMemory: 0` where Docker 29 omits it, i.e. what
  the Ussuri-era daemons returned; the module's decision logic and file are untouched. Without it the module fails on
  every existing container on this Docker (a1x).
- **The venv differs from the study's shared venv** in requests/urllib3 (L1), PyYAML 5.3.1 and its own compat `.pth`.
- **Stand-ins:** the RabbitMQ broker (ignores SIGTERM by design; real RabbitMQ shuts down on SIGTERM), `heat-manage`
  and `openstack`, and the placeholder config files. No RabbitMQ (Ussuri: 3.8; bionic has 3.6) or other Cloud Archive
  package was used. rsync is real.
